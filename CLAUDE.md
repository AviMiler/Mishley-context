## Module split rationale

`content.js` is the orchestrator: state, mount, the central `wireEvents` switchboard, the edit-form, the small context-list render, and init. Everything else lives in a focused module:

- **`ui-modals.js`** — pure overlay/dialog UI. No business state. Backup export/import stays in `content.js` because it mutates `state.blocks`; the storage-usage panel (D3, 2026-08-04) follows the same rule — `ui-modals.js` only renders `#storageInfoOverlay`, the actual `chrome.storage.local` reads/orphan-sweep live in `content.js` and are passed in as deps.
- **`history-view.js`** — the active project (global selection, persisted). Owns `loadActiveProjectId`/`setActiveProjectId`, the project instructions/documents rendering for whichever project is active (`renderProjectContext`), project bookmarking/scanning/file-picking, all row/project dropdowns, and the shared floating-menu host (`positionHiDropdown`/`closeHiDropdown`, also used by `code-tree.js` and `ctx-meter.js`). Projects-only since 2026-08-04 — it used to also own the conversation-history world (History-tab list, per-message preview panel, `buildConversationInjectionText`/`formatTranscript`/`buildHistoryMessages`), all removed along with that feature; the filename wasn't changed (see DECISIONS.md).
- **`document-handler.js`** — project document lifecycle (add/remove/toggle, token estimation, Office text extraction) and the code-project folder scanner (`scanCodeProject`, `syncCodeProjectDocuments`). No UI of its own.
- **`dep-graph.js`** — pure, static (no-AI) import/reference graph builder for scanned code projects (JS/TS/JSX + C#/Razor + CSS `@import`). No UI, no storage access.
- **`code-tree.js`** — the inline file-tree picker for hand-selecting which code-project files to inject, rendered directly into the open project's documents section (not a modal), including the "load with dependencies" menu backed by `dep-graph.js`. Folder rows carry their own checkbox (checked/unchecked/indeterminate over their descendant files) to select or clear an entire folder in one bulk save. Its dependency manager also stores a separate root-only transitive ignore list per file (`depLoadIgnores`) that only applies when that file is the load root.
- **`fs-handles.js`** — IndexedDB wrapper for storing `FileSystemDirectoryHandle` objects (chrome.storage.local can't hold them).
- **`chat-features.js`** — interactions with the page's chat. General Memory render+auto-inject, manual injection of selected blocks (incl. a selected project's instructions), quick commands. The conversation-capture/auto-save flow this module used to also own was removed 2026-08-04 along with the conversation-history feature.

Each module exposes `init(deps)` (matching the `ctx-meter.js` pattern). `content.js` calls each module's `init` during `mountUI` and passes a shared `state` object plus the functions the module needs.

## Storage Schema (blocks)

```
{ "b_<ts>_<rand>": { id, title, content?, kind?, updated, pinned?, autoLoad?, projectId?,
                     documents?, isCodeProject?, dirHandleId?, lastScanned?, depGraphOverrides?, ignorePatterns?, trigger? } }
```

**Storage layout v3 (2026-08-04):** `chrome.storage.local.set({ blocks })` re-serializes and rewrites the ENTIRE map on every `saveBlocks()` call (~30 call sites, including every file checkbox in the code tree) — with `depGraph` stored inline this meant rewriting a map that reached ~138MB for one real user on nearly every action, which is what froze the panel. It now lives in its own per-item key, mirroring the pre-existing `codeContent_<id>`/`docBlob_<id>` precedent:

- `depGraph_<projectId>` — the code project's scanned import graph (`storage.js#loadDepGraph`/`saveDepGraph`/`removeDepGraph`), written only on scan (`createCodeProjectBookmark`, `rescanCodeProject`). `depGraphOverrides` stays on the block exactly as before — see the paragraph below, its rationale is unchanged.
- A one-time, idempotent migration (`content.js#migrateStorage`, runs inside `loadBlocks()` right after the pre-existing `migrateCtxProjects()`) splits an existing pre-v3 `blocks` map on first load: batches of 50 blocks, writing each batch's new `depGraph_` keys and only then stripping the inline copies, so an interruption can leave data in both places but never in neither. Guarded by `ccb_storageVersion` (see Storage Keys). Progress shown via the existing `setProgress`/`clearProgress` indicator.
- `storage.js#saveBlocks` is a trailing 150ms throttle (timer not reset on subsequent calls) returning a shared promise, instead of writing on every call; `flushSaveBlocks()` writes immediately and is used by the migration, import, and a fire-and-forget `beforeunload` handler.
- **v3 also retired the conversation-history feature** (2026-08-04, see CHANGELOG.md/DECISIONS.md) — `kind:"conversation"` blocks no longer exist as a concept. The same migration now permanently deletes any surviving `kind:"conversation"` blocks and their `conv_<id>` storage (`storage.js#purgeConversationData`) rather than moving their data anywhere, per the user's explicit choice to purge rather than leave it inert (see DECISIONS.md).
- Real-browser verification of this migration (both the depGraph split and the conversation purge) against a real large profile is still pending — see AGENT_CONTEXT.md.

**Orphan cleanup + cross-tab sync (2026-08-04, closes out the original 6-phase storage/perf plan — D1–E1; Phase A above, plus this, is everything that plan produces; B/C were confirmed moot by the conversation-history removal, F1/F2 remain deliberately deferred as low-value):**

- **D1 (backup content-completeness):** `exportBackup`/`importBackupFile` (`content.js`) now include/restore the actual `codeContent_<id>`/`docBlob_<id>` content alongside `depGraphs` — a real export now round-trips a project's uploaded files and scanned code text, not just its metadata and graphs. Per the user's explicit choice, this is content-completeness only: still one synchronous `JSON.stringify`, no chunking/streaming. See "Backup export/import v3" below.
- **D2 (import orphan cleanup):** `content.js#collectAliveContentIds(blocks)` scans a blocks map for which project/doc ids currently own `depGraph_`/`codeContent_`/`docBlob_` keys; `removeOrphansForReplacedBlocks(oldBlocks, newBlocks)` diffs the before/after sets and removes storage keys the OLD data owned that the NEW data doesn't, called from `importBackupFile` right after the wholesale block replace. Closes the gap where importing a backup used to leave the previous data's content keys stranded forever.
- **D3 (storage usage panel):** `#storageInfoBtn` in Advanced Options opens `#storageInfoOverlay` — total bytes plus a per-prefix breakdown (`depGraph_`/`codeContent_`/`docBlob_`, via `storage.js#getBytesInUse`), and a manual "סרוק ונקה יתומים" button that runs the same sweep D4 runs automatically. `ui-modals.js` owns only the dialog UI; `content.js#getStorageUsageBreakdown`/`sweepOrphanKeys` own the actual `chrome.storage.local` access and are passed in as deps (`getStorageUsage`/`runOrphanSweep`) — UI modules never touch storage directly, matching this codebase's established module-boundary convention.
- **D4 (automatic orphan GC):** `content.js#sweepOrphanKeys()` (shared with D3's manual button) lists every key (`storage.js#listAllKeys`, feature-detected `chrome.storage.local.getKeys()`, Chrome 130+ — resolves `null`, not an empty array, when unavailable, so a caller can't mistake "can't enumerate" for "nothing to clean"), computes the alive set from the CURRENT `state.blocks` via `collectAliveContentIds`, and removes anything `depGraph_`/`codeContent_`/`docBlob_`-prefixed that isn't in it (`conv_` is deliberately excluded — see `storage.js`'s header comment; that space was a one-time purge, not an ongoing sweep target). `maybeRunAutomaticOrphanGc()` throttles this to once per 24h via `chrome.storage.local["ccb_lastOrphanGC"]`, fires from `init()` without ever blocking panel load, and updates the timestamp even on a failed sweep so a persistent failure can't retry-storm every load.
- **E1 (cross-tab sync):** a `chrome.storage.onChanged` listener (`content.js`) refreshes `state.blocks` and re-renders when another tab writes to `blocks`. Guarded by a monotonic generation counter — `_writeGeneration` increments on every `saveBlocks()` call, `_lastSavedGeneration` advances (monotonically) to the exact generation a write captured once that write is durably confirmed; the listener only applies an incoming snapshot when `_writeGeneration === _lastSavedGeneration`, i.e. when there is no local edit — self-originated or about to be overwritten by an external one — that isn't yet confirmed durable. This is NOT a boolean "ignore my own echo" flag — two earlier designs (a boolean flag, then no guard at all) were both found genuinely broken by `verify-agent`, including a real race reachable from ordinary single-tab rapid editing, not just multi-tab use — see DECISIONS.md for the full account, it's worth reading before touching this code. Separately, a `_blocksMutationDepth` counter (`beginBlocksMutation()`/`endBlocksMutation()`, a counter not a boolean so nested calls — e.g. `importBackupFile` calling `migrateStorage` internally — compose correctly) guards the listener during multi-step operations that mutate `state.blocks` across several `await`s before a single trailing `saveBlocks()` (a scan writes to the project object directly, saves once near the end): `migrateStorage`, `importBackupFile`, `history-view.js#createCodeProjectBookmark`/`#rescanCodeProject` are all wrapped in it.
- Real-browser verification of D1–E1 (same standing caveat as the rest of this plan) is still pending — see AGENT_CONTEXT.md.

`documents` (kind: "project" only): array of `{ id, name, type, size, added, enabled, preview, estimatedTokens, content?, hasBlob?, isManuallyAdded?, fileHandleId?, favorite? }`. `favorite` (code projects only, 2026-08-05): `boolean`, defaults falsy/absent — toggled via the file tree's star button (`document-handler.js#toggleFavorite`), independent of `enabled`; a favorited doc renders in BOTH the new favorites section and its normal tree/manual-list spot (not moved). File blobs live in `chrome.storage.local["docBlob_<id>"]`; code-project file text lives in `chrome.storage.local["codeContent_<id>"]` — never inline on the doc, so scanning a large folder doesn't bloat every `saveBlocks()` call. Requires the `unlimitedStorage` permission. `isManuallyAdded` (code projects only, 2026-07-29): `boolean` — true if the user manually selected the file via `showOpenFilePicker()`, absent/false for files discovered by `scanCodeProject`. `fileHandleId` (when `isManuallyAdded === true`): string key in IndexedDB (via `fs-handles.js`) for the persistent `FileSystemFileHandle` so the file can be re-read on rescan even if moved to a different location. On rescan, manually-added files are re-verified: if readable, content is silently refreshed (file.text() replaces doc.content); if unreadable (deleted, moved away, permission revoked), the doc is removed along with its codeContent and fs-handle, and the filename is reported in a toast.

`ignorePatterns` (code projects only, `isCodeProject: true`): `string[]` of user-typed file/folder names or `*`-globs excluded from `scanCodeProject`, edited via the ignore-list dialog next to the documents header's refresh button. Defaults to `[]`.

`depGraphOverrides` (code projects only, 2026-07-27): `{ [relativePath]: { added: string[], removed: string[] } }` — manual per-file dependency edits made in `code-tree.js`'s dependency manager (see Features overview). Kept **separate** from the scanned graph deliberately: `rescanCodeProject` overwrites the graph wholesale on every scan, while `depGraphOverrides` is written only by `history-view.js#setFileDependencyOverride` and never touched by a scan, so a manual choice survives a rescan and keeps overriding the freshly-scanned default. The scanned graph itself lives in its own `depGraph_<projectId>` key, not inline on the block (see "Storage layout v3" above) — this separation and its rationale are unchanged, only the graph's own storage address moved. `code-tree.js` now caches the raw graph module-side (`loadRawGraph()`/`rawGraph()`/`hasRawGraph()`) and `effectiveGraph()` reads through that cache; every reader of the graph (used by both the manager and the pre-existing "load with dependencies" menu) applies overrides via `dep-graph.js#applyOverrides(rawGraph, depGraphOverrides)` rather than reading the scanned graph raw.

`trigger` (any block, 2026-07-28 — Phase 4.2): optional `string`, e.g. `"/sum"` — always normalized to carry its own leading `/` on save (`content.js#saveEdit`), validated for no whitespace and for uniqueness case-insensitively across every block. Edited via `#editTrigger` in the shared edit form (so any block type — general, project-owned, GM, project instructions — can carry one). Powers the quick-command menu (see Features overview); absent/`undefined` means the block has no shortcut.

- No `kind` → Context view block (general if no `projectId`; project-owned if `projectId` is set)
- `kind: "project"` → the single unified project entity — instructions (`content`), own text blocks (child blocks with `projectId`), documents, and/or code-project scanning. Selected via the global project bar at the top of the panel.

**`kind: "conversation"` is retired** (2026-08-04, along with the whole conversation-history feature — see CHANGELOG.md/DECISIONS.md). Any surviving block of this kind is deleted, not migrated, by `content.js#migrateStorage` (see "Storage layout v3" above).

**`kind: "ctx-project"` is retired.** It was the old Context-tab "grouping of text blocks only" entity. On load, `content.js#migrateCtxProjects()` (idempotent) rewrites any surviving `ctx-project` block to `kind: "project"` (filling `documents: []`, `isCodeProject: false`), keeping the same `id` so child blocks' `projectId` links are preserved. There is now one project concept, not two.

**Project-owned text blocks (`projectId` field):**
A regular context block (no `kind`) may have `projectId` pointing to a `kind: "project"` block. They render together with general blocks in the unified `#list` via `content.js#renderUnifiedBlocksList()` — project-owned ones only appear while their project is the active one (global selector), tagged with `.ctx-proj-tag` (project title, always visible). General blocks (no `projectId`) always show regardless of the active project.
Since the shared `#editView` add/edit form covers the whole panel (no project context visible behind it), `openEdit()` in `content.js` shows a small `#editProjectTag` pill (folder icon + project title) above the title field whenever the block being edited has a `projectId` — or, for a brand-new block, whenever a project is currently active (`state.currentProjectId`) — otherwise it's hidden.

Mechanism: `content.js#state.injectionStack` is a real LIFO array of injection ids; `injectTracked(text, mode)` (the one entry point for both call sites now, replacing direct `inject.injectIntoInput` calls) wraps each injection's text with its own marker pair — `[[CCB:INJ:<id>]]`/`[[CCB:INJ-END:<id>]]`, `id` from `generateInjectionId()` — before injecting, then pushes the id on success (clearing the whole stack first if `mode === "replace"`, since that wipes every earlier marker along with the box). `undoLastInjection()` pops the top id and calls `inject.js#removeMarkedSpan(start, end)` to find and remove exactly that marked span, leaving every other injection's block untouched. Two reasons the design moved to markers instead of comparing whole-box text snapshots: (1) correctness — a small literal bracket+id token survives the site's own contenteditable DOM handling far more reliably than a full-text equality check, and (2) it happens to also fix a real perf bug found in the same session: the ORIGINAL undo read the whole box via the layout-forcing `innerText` getter and rewrote it via `"replace"` mode, which unconditionally tears down and rebuilds the ENTIRE contenteditable DOM (`replaceContentEditable`) — an O(whole box) cost paid on every undo click regardless of how small the removed span was, which was genuinely slow/hanging after a large "טען קבצים" load. `removeMarkedSpan`'s contenteditable path instead walks text nodes via `textContent` (non-reflowing, unlike `innerText`) with a `TreeWalker` to locate both markers, then deletes only the range between them via a native `Range.deleteContents()` — O(removed size), not O(whole field); the plain-`<textarea>`/`<input>` path is untouched (`.value` get/set has no DOM tree to rebuild, so it was never the slow one). Deliberately does **not** hook into the auto-inject-at-start or per-message "every mode" paths (`chat-features.js#_doInject`/`_interceptSend`) — those either auto-send immediately or fire at the instant of a real send, so tracking them for undo would be both redundant and wrong. `state.injectionStack` is force-cleared (`= []`) on the two "fresh chat" resets (`ccb:urlchange`, new-chat click delegation) — each also calls `syncUndoInjectBtn()` directly so the undo button's visibility/count refreshes immediately. The pre-existing `[[CCB:INJECTED]]`/`[[CCB:CTX]]` markers (used by `_interceptSend`'s double-wrap guard) are untouched by this — the new per-injection marker only wraps AROUND them, never replaces them.
- **Quick commands (Phase 4.2, 2026-07-28, reworked same day for chaining)** — any block (general, project-owned, GM, or project instructions — the shared edit form covers all of them) can carry an optional `trigger` (`block.trigger`, e.g. `"/sum"` — see Storage Schema). Typing `/` in the CHAT PAGE's OWN input (not this panel — the actual site's compose box) opens a floating menu, `#quickCmdMenu`, listing every block with a trigger whose text (after the `/`) starts with whatever's typed so far, live-filtered on every keystroke; a space typed after the command word closes it (the interaction is over — either something was picked, or this is just a message that happens to start with `/`). ArrowUp/ArrowDown move the highlighted row, Enter/Tab selects it, Escape closes. Modeled on invoking a skill in Claude Code. **Trigger detection is NOT "the whole box starts with `/`"** (the original design, which meant a second quick command could never be typed right after a first one — the box no longer started with `/` once it held injected content) — `chat-features.js#_qcRelevantSuffix(raw)` requires only the text AFTER the last completed injection's own `[[CCB:INJ-END:...]]` marker (if any) to start with `/`, falling back to the whole box when there's no marker yet (a fresh box). This is what lets multiple quick commands (and manual injections) be chained one after another. **Word-boundary fix (2026-08-05):** within that relevant suffix, the trigger check used to require the "/" to sit at position 0 of the WHOLE suffix (`relevant.startsWith("/")`) — so typing an ordinary sentence first and only THEN adding "/cmd" at the end (e.g. "hello /sum", no injection yet — reported on the internal chat site, where this usage pattern is common; Gemini usage happened to always start messages with "/" so the same limitation was never hit there) never opened the menu. `_handleQuickCommandInput` now matches `relevant` against `/(?:^|\s)(\/\S*)$/` — the LAST whitespace-delimited token, anchored to the end of the string, required to start with "/" and be preceded by whitespace or the very start of the segment (so "hello/sum," glued mid-word, still correctly does not trigger). Everything downstream (`afterSlash`, `_qcMatchesFor`, the already-correct chained-after-a-completed-injection case) is unchanged. **Prepend-to-front-of-box fix (2026-08-05, same session):** selecting a command used to land its injected content exactly where the typed "/query" text sat — so a command typed after other free text (the very case the word-boundary fix above just enabled) left the injected block stranded after that text instead of in the front-of-box "injection area" every other manual injection uses. `content.js#injectQuickCommand` now does this in two steps: `replaceTrailingText(typedText, "")` deletes just the typed "/query" tail (same primitive as before, called with an empty replacement instead of the wrapped block), then `injectIntoInput(wrapped, "prepend")` — the same primitive the footer "טען פרומפטים" button uses — inserts the wrapped block at the very front. Chained quick commands now correctly stack newest-first at the front, matching `injectTracked`'s pre-existing stacking order. Selecting a command computes the exact same framed text `injectSelected()` ("טען פרומפטים") would produce for that one block alone — `chat-features.js#buildFramedBlockText(blocks)` was extracted out of `injectSelected` specifically so both paths share one formatting rule (GM alone → `FRAMING_GM`, everything else → `FRAMING_MANUAL`) — then deletes the typed `"/query"` TAIL of the box via `inject.js#replaceTrailingText(oldText, "")` (renamed+re-anchored from an original `replaceLeadingText`, which assumed `oldText` sat at absolute position 0 — now it's anchored at `fullLen - oldText.length` through the field's true end, since `oldText` is the box's tail, not necessarily its entirety; a `TreeWalker`+`Range` surgical edit, same non-`innerText`/non-whole-field-rebuild discipline as `removeMarkedSpan` above) before prepending the wrapped block to the front via `injectIntoInput(wrapped, "prepend")` (see the 2026-08-05 fix above — `replaceTrailingText` itself is unchanged, only how `injectQuickCommand` uses it) and participates in the SAME undo stack as any other injection (`content.js#injectQuickCommand`, built on the same `wrapForTracking`/`commitTrackedInjection` helpers `injectTracked` uses — **never resets the stack**, since an earlier chained command's marker may legitimately still be sitting earlier in the box and remains a valid undo target). `findOffsetPosition` (shared internal helper) has a boundary rule worth remembering: when the target offset lands EXACTLY on a text-node boundary, it peeks one text node ahead (skipping any intervening `<br>` block-separator automatically, since the walker only visits text nodes) rather than anchoring at the end of the current node — anchoring at "end of current node" would sit BEFORE a separating `<br>` instead of after it, gluing two chained blocks onto the same line (a real bug caught by `verify-agent` during Stage 3, fixed before shipping). `#quickCmdMenu` is positioned via the chat page's own input's `getBoundingClientRect()` (it can be anywhere on the host page, unrelated to where this sidebar sits) and rendered as a `position:fixed` SIBLING of `.panel` in the shadow root — not nested inside it — the same reasoning already established by `#filePreviewView`/`#depManagerView`: a fixed descendant of the shadow root already visually escapes the panel's own bounds and covers the whole viewport, so anchoring this menu to an arbitrary point on the host page works the same way; it also needs its own explicit `pointer-events: auto` (see Rules) since the shadow host is `pointer-events:none` by default — missing this was a real, separately-fixed bug (menu rendered but nothing in it was clickable). Rows are built via `createElement`+`.textContent`, never `innerHTML`, since block titles/triggers are arbitrary user text. The keydown listener (`chat-features.js#installQuickCommandWatcher`, called from `chat.init()` **before** `installSendInterceptor()`) additionally calls `e.stopImmediatePropagation()` when selecting via Enter/Tab, so a command-selecting Enter can never also fall through to the unrelated per-message "every mode" send-interceptor logic or the site's own send-on-Enter handling; the Enter branch excludes `e.isComposing`, matching the IME-safety convention already used elsewhere in this file. Trigger uniqueness is validated case-insensitively across every block on save (`content.js#saveEdit`), matching the case-insensitive prefix match used at typing time.

- **Razor support in the dependency graph** — `.cshtml`/`.razor` files reuse the same C# class/namespace symbol table as `.cs` files (`dep-graph.js#analyzeRazorFile`): any known type name referenced anywhere in the markup (`@model`, `@inject`, tag helpers, embedded `@{ }` blocks) becomes an edge to that type's file, filtered by `@using` directives the same way C# `using`s filter candidates. - **AST-first symbol extraction (2026-07-23)** — `dep-graph.js`'s symbol layer for `.cs` and `.js`/`.jsx`/`.mjs`/`.cjs` now comes from **tree-sitter** (real grammar-level AST, WASM) instead of regex. Placement here (not earlier) is deliberate: a session iframe's own `sessions.js` instance is already unconditionally hidden by the `isInsideOwnIframe()` branch regardless of what its own `matchMedia` would report, so whether `display-mode` propagates into a same-origin iframe embedded in a standalone window is a non-issue — the app-mode check only ever needs to run for, and only ever affects, the top-level frame. `installF5Guard()` staying installed before this check (unconditionally, for every frame) is harmless: in a non-app-mode tabbed window `_activeId` can never leave `NATIVE_ID`, since `switchSession()` is only reachable from the now-gated `loadSessions().then()` callback, so the F5 guard's session-tab branch is permanently unreachable there. **Two caveats, flagged explicitly rather than folded into the standard disclaimer:** (1) whether a raw `chrome.exe --app=URL` command-line launch (not necessarily a formally "installed" PWA) reliably reports `display-mode: standalone` is unverified without a real browser test — plausible (Chromium's app/popup window type is the same underlying window class used for installed PWAs) but not confirmed; (2) whether `display-mode` propagates the same way into a same-origin iframe nested inside a standalone window is likewise unconfirmed, but doesn't matter here per the placement reasoning above. **Mechanism:** tab #1 ("native") is whatever the top-level page already has loaded, never touched, never wrapped; every additional tab is a real same-origin `<iframe src="<AUTO_OPEN_URLS[0]>">` which — because `manifest.json`'s `content_scripts` is already `all_frames:true` — automatically gets its own fully independent Mishley instance mounted inside it (own shadow host, FAB, panel) with no extra wiring. `sessions.js` owns the tab strip: which iframe is visible, create/close/rename, and persisting the tab list. **Layout (reworked 2026-08-09 — the host page is no longer pushed down):** the strip visually overlaps the top ~40px of the real host page's own chat content — this is the deliberate, user-confirmed outcome, not a defect (the user explicitly accepted this tradeoff over keeping the page pushed down). `push.js#pushTop` was removed entirely (it used to inject a permanent `<style>` shifting `PUSH_SELECTOR`/`PUSH_FIXED_SELECTORS` — the site's real chat container — down by the strip's height; A session tab's close-X calls `closeSession(id)` directly, destroying the tab (removes its iframe + `_sessions` entry + storage) with **no confirmation prompt**, per the user's explicit request ("לא צריך התראה לפני סגירה") — same one-click-and-it's-gone convention as closing a real browser tab, no undo either way. Its `.sessions-tab-refresh` button calls `refreshTab(id)`, reassigning `iframe.src = iframe.src` (a real reload, not a same-URL no-op) — no-ops silently if that session's iframe was never created yet (never switched to). With edit+refresh+close all possible on one session tab inside the fixed 180px width, the label's available space is tighter (~104px) than with fewer buttons — `.sessions-tab-label`'s existing ellipsis/nowrap handles it, flagged as a cosmetic note worth a real-browser glance, not a defect. **F5 refreshes only the selected tab, not the whole real page (new round, on top of the already-committed 4187acc):** `installF5Guard()`, called as the FIRST line inside `init(deps)` — before the `isInsideOwnIframe()` early-return — so it installs in EVERY frame this content script mounts into: the top-level page AND every session `<iframe>` (each already runs its own fully independent Mishley/sessions.js instance per `all_frames:true`). This is necessary because `keydown` doesn't bubble across an iframe boundary — a top-level-only listener could never see F5 pressed while focus is inside a session iframe. Behavior: inside a session iframe, `e.preventDefault()` + `window.location.reload()` on itself (self-reload; only the active session's iframe is ever un-hidden per `render()`'s `display:none` toggling, so only it can ever hold focus). In the top-level frame, only intercepts when `_activeId !== NATIVE_ID` (a session tab is selected per that frame's own bookkeeping), then `e.preventDefault()` + `refreshTab(_activeId)` (the existing `iframe.src = iframe.src` reload). On the native tab it does nothing — F5 refreshes the real page normally, matching native's existing lack of its own refresh button. **Two caveats, flagged prominently rather than folded into the usual generic disclaimer:** (1) whether `e.preventDefault()` on a window-level `keydown` listener actually blocks Chrome's native F5 reload for a content script is genuinely unverifiable without a live browser test — no existing precedent in this codebase relies on this, and while plausible (F5 isn't one of the browser-reserved combos like Ctrl+N/T/W that JS categorically can't block), it isn't certain across focus states/Chrome versions; needs real-browser confirmation before being trusted. (2) `isInsideOwnIframe()` is a generic `window.top !== window.self` check, not scoped specifically to Mishley-created session iframes — but `installF5Guard()` only ever runs through `sessions.init()`, reachable only via `mountUI()`'s `isActiveSitePage()` URL gate, so in practice it's bounded to same-origin frames matching the target site's URL. This is the same class of edge case as the pre-existing third-party-wrapper-iframe scenario noted below under "Two items pending real-browser verification" — not a new concern.

**Mutual exclusion with the other full-pane views is conditional, not unconditional:** switching TO a non-native session tab (`switchSession`, when the frame-container is about to cover the viewport at this feature's high z-index) closes the other four `.cv-shell` views (`#filePreviewView`/`#depManagerView`/`#depPickerView`/`#onboardingView`); each of those four's own open paths calls `showNativeTab()` (a no-op if already on native) to drop the frame-container back out of view. There is no "does NOT close on panel-close" behavior to describe anymore — the strip is simply always present regardless of `setPanelOpen`'s state (subject only to the app-mode gate above, which is orthogonal to the panel), full stop. The nesting guard (`isInsideOwnIframe()`, `window.top !== window.self`) lives in `sessions.js#init()` itself (sets `#sessionsView` to `display:none` inline and returns before `render`), since the tabstrip markup is unconditionally in the template with no FAB gate to hide instead. **Storage:** `chrome.storage.local["ccb_sessions"]` — `[{ id, title, createdAt }]`, titles only, no URL/scroll/conversation state (every iframe reloads its site's base URL on a fresh page load; resuming a session at its exact prior conversation is out of scope for v1); the native tab is never stored here (identified in code by `id === "__native__"`) — its title lives in the separate `ccb_sessions_native_title` key described above; the last-active tab id lives in a third key, `ccb_sessions_last_active`, described in the bullet directly below. **Known-and-deliberately-deferred, not bugs to fix (flagged by `verify-agent`):** (1) incomplete ARIA tabs pattern — `.sessions-tabs` has no `role="tablist"`, tabs have no `aria-selected`, and the edit/close icon-buttons aren't independently keyboard-reachable (only the parent tab div is tabbable); (2) a narrow race — clicking the pencil on tab B while tab A is still mid-edit can silently discard A's in-progress unsaved rename once A's async `saveSessions()`→`render()` resolves; no data corruption, just a lost edit under rapid cross-tab pencil-clicking. (The earlier close-button `aria-label` wording nit no longer applies — the native tab has no close-X at all now, so there's nothing mislabeled.) **Two items pending real-browser verification** (neither could be checked statically): (1) whether the internal site's own CSP `frame-src` directive — independent of the already-confirmed `X-Frame-Options` — could still block the iframe; (2) `isInsideOwnIframe()` also reads `true` when the top-level Mishley instance is itself running inside a third-party wrapper iframe (the `all_frames:true` scenario in the Rules section below) — in that narrow combination, the whole strip is hidden on what the user perceives as the real top-level page.

**Per-tab "thinking" indicator (2026-08-09):** each tab pill (native included, per the user's explicit choice — every tab shows the dot when its own chat is generating a response) shows a small `.sessions-tab-thinking` dot when that tab's underlying chat is currently generating a response. **Detection** is owned by the new `thinking-indicator.js` (`window.__ccbThinking`, see Key Globals) — a `MutationObserver` on `MSG_SELECTORS.messageList` watching for `.waiting-indicator`, running in EVERY frame (top-level + every session iframe, since each iframe is its own fully independent Mishley instance) so each frame only ever inspects its own DOM, never another frame's. **Rendering is top-level-only** (only the top-level frame's instance owns `#sessionsView`/the tab pills — `isInsideOwnIframe()` hides the strip markup in every session iframe's own instance, same as the rest of this feature), which forces an asymmetric wiring, both branches installed by `content.js#initModules()`: (1) **native tab** — sender and renderer are the SAME frame, so `content.js` passes an `onChange` to `__ccbThinking.init()` that, when `window.top === window.self`, calls `window.__ccbSessions.setNativeThinking(thinking)` directly — no messaging. (2) **session iframes** — each iframe's own `onChange` instead does `window.top.postMessage({ type: "ccbThinking", thinking }, window.location.origin)`; `sessions.js#installThinkingListener()` (top-level frame only, installed in `init()` right after the `isInsideOwnIframe()` branch) listens for these, origin-checked, matching `event.source` against the `_iframes` Map's `contentWindow` to resolve which session the message came from, then sets `_thinking.set(id, !!data.thinking)` and re-renders that pill. `__ccbThinking.watch()` is called at the same 2 call sites `ctx-meter.js#watchConversation()` already is (mirrors its idempotent re-arm pattern, so it picks up the message-list container once the chat page actually mounts it). `sessions.js#closeSession()` also does `_thinking.delete(id)` so a closed tab's stale state can't linger. Works correctly even when `SESSIONS_ENABLED === false` — `setNativeThinking()` stays callable even though `sessions.js`'s own `init()` early-returned, since it doesn't touch anything `init()` would have set up (confirmed by `verify-agent`). **`.waiting-indicator` itself is NOT verified against the real site** — no other reference to that selector exists anywhere else in the codebase, and there's no static way to confirm the site adds/removes it via a mutation the observer's `childList`+`subtree` config actually catches (vs., say, an `innerHTML` rewrite that still fires `childList` but wasn't explicitly tested) — flagged prominently, not folded into the standard "not yet browser-verified" disclaimer, since this one specific selector is the single point of failure for the whole feature. Visual treatment (dot placement/color/pulse animation) was a judgment call (no explicit user spec) — `ui-styles.js`'s `.sessions-tab-thinking` — reasonable default, open to adjustment post-hoc without touching the underlying mechanism.

**Native tab hidden (CSS-only) whenever any session exists, and auto-switch-to-last-active on load (2026-08-09):** user request — "no need to show the native tab at all if there are several [session tabs]; when the site opens it should immediately switch to a secondary tab, and we hide the native tab with CSS." Two combined behaviors, both in `sessions.js`+`ui-styles.js`: (1) **Pill hiding.** `buildTabPill(session, {...,hidden})` gained a `hidden` option that appends a `sessions-tab-hidden` class (`ui-styles.js`: `display: none`); `render()` passes `hidden: _sessions.length > 0` for the native tab's pill only (session pills never get this option). Deliberately a CSS-only hide, not an omitted DOM node, per the user's literal wording and so the pill's presence/absence doesn't need to be reasoned about separately from its visibility — the node still exists, just not shown. **This does NOT gate `switchSession(NATIVE_ID)` itself** — `showNativeTab()` (called from `code-tree.js`'s file-preview/deps-manager/dep-picker and `ui-modals.js`'s onboarding, for the pre-existing mutual-exclusion pattern described above) stays fully callable regardless of the pill's hidden state; the hide is purely visual, confirmed by `verify-agent` to never gate the function. When the last session closes, the native pill reappears automatically — `hidden` is recomputed fresh from the live `_sessions.length` on every `render()`, no separate un-hide code needed. (2) **Auto-switch on load.** New storage key `ccb_sessions_last_active` (see Storage Keys table) — `switchSession(id)` now also fire-and-forgets `chrome.storage.local.set({ ccb_sessions_last_active: id })` on every call, including switches to native (a stray recorded `"__native__"` is harmless — see below). `loadSessions()` reads it in the same batched `get([...])` call as `ccb_sessions`/`ccb_sessions_native_title`. In `init()`, once `loadSessions()` resolves: if `_sessions.length > 0`, the module calls `switchSession(remembered)` instead of a bare `render()`, where `remembered` = the stored last-active id if it still matches an entry in `_sessions`, else a fallback (see below) — so a page reload with existing session tabs lands directly on a session, never native, matching the user's request. If `_sessions.length === 0`, behavior is unchanged (renders on native, nothing to switch to). A stored `"__native__"` value never matches a `_sessions` entry, so it always falls through to the fallback — which is exactly the wanted behavior (never auto-land on native when sessions exist, even if native was the last tab visited before a session was added). **Fallback default — the building agent's own judgment call, not user-specified:** when no remembered id exists or it no longer matches any current session (e.g. that session was closed), the fallback is the last entry in `_sessions` (the most recently created session — confirmed by `verify-agent` that only `push`/`filter` ever touch this array, so array order genuinely reflects creation order). This default was surfaced to the user via the coordinator's summary rather than gated on a blocking question; the user has not objected as of this writing, but it remains an assumption, not a confirmed requirement — worth re-confirming if it ever needs to change. `verify-agent` Go: confirmed no keyboard-trap/focus issue on the hidden pill (`display:none` removes it from tab order, nothing calls `.focus()` on it), confirmed `closeSession()` correctly un-hides native when the last session closes, confirmed the stray-`"__native__"`-write edge case is inert.

## Rules

- **Content scripts run in all same-origin frames, not just the top frame** (`manifest.json`'s single `content_scripts` entry sets `"all_frames": true`, added 2026-08-06). This lets Mishley keep working when the target chat site is embedded in a same-origin iframe by some other extension (e.g. a third-party "multi-tab" wrapper extension the user tested with, which hides the top document's body via `display:none` and puts the real chat UI in an iframe) — without this, `msg-nav.js`'s `document.querySelectorAll` and `inject.js#findInput()` only ever search the top-level `document` and silently find nothing inside such a wrapper. Runtime activation is still fully gated by `ACTIVE_SITE`/`AUTO_OPEN_URLS` in `config.js` regardless of which frame the script loaded into — `all_frames` only controls where the script CAN run, not whether it actually mounts UI. **Real-browser verification against the actual target site + the third-party wrapper extension is still pending** — Stage 3 confirmed this statically (manifest validity, the cross-tab-sync generation-counter design already handling a second concurrent frame instance safely) only.
- After every change: update this file and `ARCHITECTURE.md`
- Keep the current split — never re-merge `ui-modals.js` / `history-view.js` / `chat-features.js` / `content.js`
- When editing dialogs/settings: read `ui-modals.js`. For projects: `history-view.js`. For GM/inject-selected/quick commands: `chat-features.js`. For mount/wiring/state/edit-form/context-list: `content.js`. For styles: `ui-styles.js`. For prompts defaults: `config.js`.
- Modules access shared state via `_deps.state` and shared helpers via the `_deps` object passed to `init()`. Never read state directly from `window.__ccb*` outside of `init`.
- **New top-level shadow-root elements need `pointer-events: auto` explicitly.** `#ccb-host` (the shadow host, `content.js`) is deliberately `pointer-events:none` — a 0×0 fixed div that must never block clicks on the real page — so `.fab`/`.panel` (and any future sibling like `#quickCmdMenu`) each opt back in themselves. Forgetting this makes an element render fine but be completely unclickable (2026-07-28 bug, see AGENT_CONTEXT.md/CHANGELOG.md).
