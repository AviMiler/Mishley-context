## Module split rationale

`content.js` is the orchestrator: state, mount, the central `wireEvents` switchboard, the edit-form, the small context-list render, and init. Everything else lives in a focused module:

- **`ui-modals.js`** — pure overlay/dialog UI. No business state. Backup export/import stays in `content.js` because it mutates `state.blocks`.
- **`history-view.js`** — the active project (global selection, persisted) + conversation world. Owns `loadActiveProjectId`/`setActiveProjectId`, the project instructions/documents rendering for whichever project is active (`renderProjectContext`), project bookmarking/scanning/file-picking, the History-tab conversation list (filterable by the active project), the per-message preview panel, and all row/project dropdowns. Owns the framing builders (`buildConversationInjectionText`, `formatTranscript`, `buildHistoryMessages`). (Kept as its own module even though the project bar/context now render above and inside the Context tab — the split is by responsibility, not by which tab hosts the DOM.)
- **`document-handler.js`** — project document lifecycle (add/remove/toggle, token estimation, Office text extraction) and the code-project folder scanner (`scanCodeProject`, `syncCodeProjectDocuments`). No UI of its own.
- **`dep-graph.js`** — pure, static (no-AI) import/reference graph builder for scanned code projects (JS/TS/JSX + C#/Razor). No UI, no storage access.
- **`code-tree.js`** — the inline file-tree picker for hand-selecting which code-project files to inject, rendered directly into the open project's documents section (not a modal), including the "load with dependencies" menu backed by `dep-graph.js`. Folder rows carry their own checkbox (checked/unchecked/indeterminate over their descendant files) to select or clear an entire folder in one bulk save.
- **`fs-handles.js`** — IndexedDB wrapper for storing `FileSystemDirectoryHandle` objects (chrome.storage.local can't hold them).
- **`chat-features.js`** — interactions with the page's chat. General Memory render+auto-inject, manual injection of selected blocks (incl. a selected project's instructions), "save chat" capture flow (exported but unwired from any UI control as of 2026-07-19 — auto-save is the active path), inline 💾 save button on AI messages.

Each module exposes `init(deps)` (matching the `ctx-meter.js` pattern). `content.js` calls each module's `init` during `mountUI` and passes a shared `state` object plus the functions the module needs.

## Storage Keys

| Key                                | Owner          | Shape                                                  |
| ---------------------------------- | -------------- | ------------------------------------------------------ |
| `chrome.storage.local.blocks`      | content.js     | `{ [id]: block }` — see schema below                  |
| `chrome.storage.local.ccb_prompts` | prompts.js     | `{ manualIntro, manualOutro, gmIntro, gmOutro, ... }` |
| `chrome.storage.local.ctxWindow`   | content.js     | `number` (tokens, used by the meter)                  |
| `chrome.storage.local.ccb_scanSettings` | content.js | `{ denyDirs, denyFilenames, codeExtensions, maxFileSizeKb }` — global code-project scan rules |
| `chrome.storage.local.activeProjectId` | history-view.js | `string \| null` — the globally selected project (see Features overview) |

## Storage Schema (blocks)

```
{ "b_<ts>_<rand>": { id, title, content?, messages?, tags?, kind?, updated, pinned?, autoLoad?, projectId?,
                     documents?, isCodeProject?, dirHandleId?, lastScanned?, depGraph?, ignorePatterns? } }
```

`documents` (kind: "project" only): array of `{ id, name, type, size, added, enabled, preview, estimatedTokens, content?, hasBlob? }`. File blobs live in `chrome.storage.local["docBlob_<id>"]`; code-project file text lives in `chrome.storage.local["codeContent_<id>"]` — never inline on the doc, so scanning a large folder doesn't bloat every `saveBlocks()` call. Requires the `unlimitedStorage` permission.

`ignorePatterns` (code projects only, `isCodeProject: true`): `string[]` of user-typed file/folder names or `*`-globs excluded from `scanCodeProject`, edited via the ignore-list dialog next to the documents header's refresh button. Defaults to `[]`.

- No `kind` → Context tab block (general if no `projectId`; project-owned if `projectId` is set)
- `kind: "conversation"` → History tab; may have `projectId` (stamped from the active project at creation)
- `kind: "project"` → the single unified project entity — instructions (`content`), own text blocks (child blocks with `projectId`), documents, and/or code-project scanning. Selected via the global project bar above both tabs.
- `id: "__general_memory"` → General Memory card (kind: `"general_memory"`, has `autoLoad`)

**`kind: "ctx-project"` is retired.** It was the old Context-tab "grouping of text blocks only" entity. On load, `content.js#migrateCtxProjects()` (idempotent) rewrites any surviving `ctx-project` block to `kind: "project"` (filling `documents: []`, `isCodeProject: false`), keeping the same `id` so child blocks' `projectId` links are preserved. There is now one project concept, not two.

**Project-owned text blocks (`projectId` field):**
A regular context block (no `kind`) may have `projectId` pointing to a `kind: "project"` block. They render together with general blocks in the Context tab's unified `#list` via `content.js#renderUnifiedBlocksList()` — project-owned ones only appear while their project is the active one (global selector), tagged with `.ctx-proj-tag` (project title, always visible). General blocks (no `projectId`) always show regardless of the active project.
Since the shared `#editView` add/edit form covers the whole panel (no project context visible behind it), `openEdit()` in `content.js` shows a small `#editProjectTag` pill (folder icon + project title) above the title field whenever the block being edited has a `projectId` — or, for a brand-new block, whenever a project is currently active (`state.currentProjectId`) — otherwise it's hidden.

## Active Site

Change `ACTIVE_SITE` in `config.js` → `"gemini"` or `"internal"`.
The UI and summarizer are gated to the active site's `AUTO_OPEN_URLS`, so they stay inert on other sites.

## Features overview

- **Sidebar** with FAB strip on the left, opens with click or Ctrl+Shift+L. Width is `SIDEBAR_WIDTH` in `config.js` (380px; `push.js` + full-page overlays derive from the same constant). **Opens to the Context tab by default** (`.tab.active`/`.tab-pane.active` on `#pane-context` in `ui-template.js`) — the History tab's `#searchHistory` autofocus in `content.js#setPanelOpen` is guarded to only fire when the History tab is actually the active one. **Tab order:** Context is the first `.tab` in the DOM, History second — in the panel's RTL layout that puts Context on the right, History on the left (first flex child in `.tabs` renders at the RTL start/right edge). `moveTabIndicator`/tab-click wiring read live DOM order (`querySelectorAll(".tab").forEach`, `tab.offsetLeft`), so reordering the two `<div class="tab">` elements is the only thing that needs to change to flip which side either tab sits on.
- **Global project bar** (`#globalProjectBar`) — sits above both tabs (visible regardless of which is active), never hides. A **custom dropdown** (`#projectSelectBtn` trigger + `#projectSelectDropdown` panel, `history-view.js`'s `renderProjectSelect`/`toggleProjectSelectDropdown`/`closeProjectSelectDropdown` — **not** a native `<select>`, so code projects can carry a real SVG folder icon instead of a text tag, and the dropdown matches the panel's own visual language: `.project-select-item` rows styled like the rest of the app, `.active` row highlighted, click-outside + Escape to close) drives `state.currentProjectId`, the single **active project** for the whole panel. Persisted across sessions in `chrome.storage.local.activeProjectId` via `history-view.js#loadActiveProjectId`/`setActiveProjectId` (loaded once inside `content.js#loadBlocks`). `#projectEditBtn` (3-dot menu, hidden when no project is active) is the LAST child of `#globalProjectBar` — in this RTL layout that puts it at the far-left edge, after the "+" buttons — and opens `historyView.openProjectDropdown`, a 2-item menu ("שנה שם" / "מחק") reusing the shared `#hiDropdown` host element, same pattern as `openHiDropdown` for history rows. Rename now works identically for regular and code projects (previously code projects had no rename at all); delete for a code project reads "מחיקת פרויקט" (project deletion), not "הסרת סימניה" (bookmark removal) as it used to — the underlying `fs-handles.js` mechanism is still internally called a "bookmark" (`createCodeProjectBookmark`), but no user-facing text uses that word for a project anymore. The dropdown's earlier "load all"/"refresh" items (code-project-only, from before rename/delete were unified into one menu) are gone as redundant with the file tree's own select-all + `#codeProjectRefreshBtn`. The "+ פרויקט"/"+ פרויקט קוד" buttons (`addProjectBtn`/`addCodeProjectBtn`) create new ones (auto-selecting the new project).
- **Context tab** — one unified view, no sub-tabs. Context-window meter at the top, then a single collapsible **`#blocksSection`** (`section-header` + `#blocksCollapseBtn`, same collapse pattern as the History tab's conversation list — toggling it hides `#blocksSectionBody` as a whole; the header's right side (`.section-head-right`) holds only **`#addBtn`** ("+ new block") since 2026-07-19 (there is no dedicated "load instructions" button — see below), styled as a small square/light icon button matching `#addProjectBtn`/`#addCodeProjectBtn`/`#projectEditBtn` — see the shared selector in `ui-styles.js`) holding **everything injectable**: the General Memory card (`#gmCard`), the active project's **instructions card** (`#projectInstructionsCard`, directly below GM, hidden when no project is active), and the **unified prompts list** (`#list`) — general blocks (no `projectId`) plus the active project's own blocks, project-owned rows carrying a `.ctx-proj-tag` pill with the project's title, always visible (not just when selected). Both GM and the instructions card are built dynamically (`chat-features.js#renderGeneralMemory` / `history-view.js#renderProjectInstructionsCard`) as `.gm-card`s: a header (select-for-inject checkbox + autoLoad toggle + title — **both cards have the checkbox**, not just GM, since 2026-07-19) and, when autoLoad is on, an `.auto-badge` below. **Neither has a dedicated edit button** — clicking anywhere on the card opens the shared block-edit form (`content.js#openEdit`) prefilled with its title/content, exactly like clicking a row in `#list`; the toggle/checkbox `stopPropagation()` so toggling them doesn't also open the form. Manually loading either GM or the active project's instructions is the same flow: tick its checkbox, then click the footer **`#injectBtn`** ("טען פרומפטים") — the project-instructions card lost its standalone `#injectInstructionsBtn` button in favor of this, so GM and instructions behave identically. `injectSelected()` (`chat-features.js`) only ever includes a selected project block's `content` (instructions), never its documents, and — like every other manual-load action in the panel — does **not** auto-send (fixed 2026-07-19; it used to click send). A block created via "+" is stamped with `state.currentProjectId` if one is active, otherwise stays general (`content.js#renderUnifiedBlocksList`/`openEdit`/`saveEdit`/`syncBlocksSection`). Each row in `#list` is `display:flex` (`.block` — fixed 2026-07-19; it was missing this despite child rules assuming it, so checkbox and title stacked instead of sharing a line) and no longer shows a redundant tag-count badge next to the title. `saveEdit()` spreads the existing block first (`{ ...existing, id, title, content, tags, updated }`) so fields the form doesn't know about — `kind`, `autoLoad`, `projectId`, and a project's `documents`/`isCodeProject`/`dirHandleId`/`lastScanned`/`depGraph` — survive instead of being dropped; the delete button stays hidden for `kind:"project"` blocks since their deletion needs the dedicated cleanup in `history-view.js#deleteProject` (child blocks, active-project reset), not the generic one-block delete. Below `#blocksSection` (outside the collapse — its own separate toggle): for the active project, a **documents section** (`#projectDocumentsCard`, header styled identically to `#blocksSection`'s — same `.section-header`/`.section-head-left`/`.section-label`, no card background — collapsible via `#projectDocumentsToggle`/`history-view.js#syncProjectDocumentsSection`). The header's right side holds `#projectAddDocumentBtn` ("+ הוסף", regular projects only) and `#codeProjectRefreshBtn` (code projects only — replaces the old standalone "last scanned" info box, which is gone; the scan age now shows as the button's `title` tooltip). Content is a flat list + add-document dialog for regular projects, or the **inline file tree** (`code-tree.js#renderInline` inside `#projectDocumentsList` — tree + per-file dependency-linking, no modal) for code projects. All driven by `history-view.js#renderProjectContext` (which also prunes any non-active project's id out of `state.selected` on every call, since only the active project's checkbox is visible), called on every `render()`. The Context-tab footer holds two equal-width, equally-styled actions: **`#injectBtn`** ("טען פרומפטים" — injects every ticked checkbox in `#list`/GM/instructions) and **`#injectDocsBtn`** ("טען קבצים" — the active project's enabled documents, see below; disabled — not hidden — whenever the project has documents but none of them, other than the always-on never-user-toggleable "structure" doc for code projects, are enabled, so it can't be clicked to inject nothing).
- **History tab** — conversation list (title-search or content-search; pin / rename / assign-to-project / delete), **filtered to the active project's conversations** whenever one is selected (`renderHistoryList`'s `state.currentProjectId` filter — "ללא פרויקט" does not filter, it shows everything). A row (`#historyProjectFilterRow`) shows "מציג שיחות של: <project>" plus a "הצג את כל השיחות" checkbox (`state.historyShowAll`, transient) to override the filter without changing the active project. The "assign to project" picker still reads the same unified `kind:"project"` blocks.
- **Conversation preview panel** — opens on click, lets you search messages, select a subset, and load them into the current chat. Clicking the same conversation row again closes the preview. Content-search hits in the History list (rows with `kind: "message"` and `messageIndex`) jump straight to the matching message inside the preview: they open the conversation, copy the History search query into `cvSearch` (so highlights show), scroll the target message into view via `scrollToMessageIndex`, and briefly flash it (`.cv-msg-flash`).
- **Conversation view — one action:** **"טען נבחרים" (`cvLoadBtn`)** — injects selected messages as context into the current chat (`buildConversationInjectionText(messages)`, no project-instructions option). Does NOT bind; current chat stays its own conversation. **Does not auto-send** — the user reviews/edits/sends manually. (Removed 2026-07-19: "המשך שיחה" resume-in-a-fresh-chat action, and the "כלול הנחיות פרויקט" checkbox — see ARCHITECTURE.md's Conversation model section for what was deleted.)
- **Auto-save chat** runs continuously in `chat-features.js#scheduleAutoSave` (2.5s debounce after each new message) — keeps a single conversation block per page load, refreshed on every message. A brand-new conversation is stamped with whatever project is active (`state.currentProjectId`) at the moment `persistConversation()` first creates its block — fixed for the conversation's lifetime; switching the active project afterward does not retroactively reassign it. Refresh or SPA navigation starts a new conversation. `chat-features.js#saveChat()` (a full scroll-to-top capture of older messages) has no UI trigger since the History tab's "שמור שיחה" button was removed 2026-07-19 — the function and its export are untouched, just unwired; auto-save is the only active save path today. `summarizer.js` separately saves a summary block on the `[[CCB:SAVE]]` marker.
- **Advanced options** popover — context-window size, backup export/import (`context-bank-backup.json`), prompts editor, and **global code-project scan rules** (`#scanSettingsBtn` → `#scanSettingsOverlay`, `ui-modals.js#openScanSettings`): the filters that used to be hardcoded in `document-handler.js` — folders to exclude, files/globs to exclude, extensions to scan, max file size (KB) — now shown **pre-filled with their built-in defaults** and editable. Three chip lists (reusing the `.ignore-patterns-*` CSS from the per-project ignore dialog), each with its own live search/filter box above it (`.scan-settings-search-input`, display-only — filters what's shown, never mutates the draft), + a number input. Persisted to `chrome.storage.local["ccb_scanSettings"]`, seeded on first load from `docHandler.getDefaultScanSettings()` and written back immediately so the dialog always mirrors what the scanner uses. Edits live in a module-scoped `_scanDraft` until Save ("אפס לברירת מחדל" only refills the draft; closing without saving discards). Saving validates (size > 0, ≥1 extension) but deliberately does **not** rescan every project — changes apply on each project's next scan/refresh. Applies to all code projects; `project.ignorePatterns` remains a separate additional exclude layer on top.
- **Prompts editor** — 5 framing pairs (manual / GM / conversation wrapper / project wrapper / file-injection wrapper); the locked technical markers (`[[CCB:INJECTED]]`, `<context>`, `<memory>`, `<transcript>`, `<project>`, `<documents>`) are visible but not editable. The SUMMARY_PROMPT editor is intentionally hidden for now. The file-injection wrapper (`FRAMING_DOCS_*`) only governs `history-view.js#injectProjectDocuments()` (the footer "קבצים" button) — the one OTHER place that builds a literal `<documents>...</documents>` block (`chat-features.js#injectSelected`, for a manually-selected project's docs) is nested *inside* an outer FRAMING_MANUAL/FRAMING_GM wrapper already and was deliberately left as-is — not a standalone top-level injection. The manual section's editor labels read "הוראות לפני/אחרי **הפרומפטים השמורים**" (not "הקונטקסט") since 2026-07-19, matching the feature's own "טען פרומפטים" terminology; all 5 `FRAMING_*_PRE` defaults in `config.js` follow the same shape (what it is → not a question/task → treat as fixed, permanent context for the whole conversation), and `FRAMING_CONV_PRE` explicitly frames its content as an excerpt from a separate prior conversation now inserted as context, not part of the live exchange. The canned `FRAMING_*_POST` auto-reply sentences ("Context loaded.", etc.) are intentionally unchanged — they're matched verbatim by `INJECTION_AUTORESPONSES` in `chat-features.js`/`history-view.js`.
- **Auto-inject at conversation start** — two independent sources, combined into a SINGLE injection: the **General Memory** (when `gm.autoLoad` is on) and the **active project's instructions** (`project.content` only, when a project is active, has instructions, and `project.autoLoad !== false`). The instructions card has its own toggle (`#projectInstructionsAutoToggle`, same `.toggle` markup as GM) — **missing `autoLoad` defaults to ON**, so pre-existing projects keep auto-loading without a migration. The `#projectInstructionsAutoBadge` ("נטען אוטומטית") reflects the toggle state, not the content — it shows even with empty instructions, signaling intent. Project **documents are deliberately excluded** — they stay behind the explicit footer "קבצים" button, since a code project's enabled files can be tens of thousands of tokens. The payload is computed at inject time (not when `tryAutoInject` is called) so switching project mid-wait doesn't inject stale instructions. Resets on URL change. `tryAutoInject` polls until both input is present *and* `msgCount === 0` (or times out at 10s) — this catches the SPA transition where the old chat's DOM lingers for a moment after navigating to a fresh chat.
- **Active-conversation marker** — `createHistoryRow` in `history-view.js` checks `state.currentConversationId === b.id` and adds an `.active` class + a pulsing dot (`.hi-active-dot`) to the row. Re-rendered on bind (continuation flow), on auto-save write, and on URL change (clearing the marker).
- **Multi-block injection** — GM-only uses FRAMING_GM, otherwise FRAMING_MANUAL (GM always goes first if mixed)
- **Project documents** — projects can hold documents: uploaded files, pasted text, or URLs, added via the restyled `#addDocumentOverlay` dialog (design-system CSS classes `.doc-paste-textarea` / `.doc-url-input`, no more inline styles). `document-handler.js` estimates tokens, extracts text (including DOCX/ODT/RTF via manual ZIP/XML parsing), and stores file blobs in `chrome.storage.local` (`docBlob_<id>`). `injectProjectDocuments()` in `history-view.js` builds the enabled doc contents into one injection, wrapped in `FRAMING_DOCS_PRE`/`POST`. **Does not auto-send** — the text lands in the chat input for the user to review, edit, or add to before sending themselves (unlike GM/manual/conversation/continuation injections, which all click send automatically). Triggered via the fixed footer `#injectDocsBtn` ("קבצים") — `content.js#syncInjectDocsBtn` hides it when the active project (`state.currentProjectId`) has no documents at all, and disables (but keeps visible) it when the project has documents but none actually enabled (excluding the always-on "structure" doc — see Code projects below); it's the single global entry point, covering both the code-project file tree and the flat regular-project document list (no per-project inject button, no separate project-picker section).
- **Code projects** — a project can instead be folder-backed (`isCodeProject: true`): `createCodeProjectBookmark()` opens `showDirectoryPicker()`, stores the handle in IndexedDB via `fs-handles.js` (chrome.storage.local can't hold handles), then `document-handler.js#scanCodeProject` recursively walks the folder (skipping `node_modules`/build output/lockfiles/config files/oversized files — all of which are now **editable global settings** rather than hardcoded, see Advanced options above) and `dep-graph.js#buildGraph` builds a static import graph. `code-tree.js#renderInline` renders a checkbox file tree **inline** in the open project's documents section for hand-picking files to inject, with a per-file "load with dependencies" menu (dependencies / dependents / full context) backed by the dep graph, and a per-folder checkbox (checked/unchecked/indeterminate, reflecting how many of its descendant files are enabled) to select or clear an entire folder in one bulk `history-view.js#enableFilesForProject` call — all static analysis, no AI, best-effort on dynamic dispatch. `CODE_EXTENSIONS` (`document-handler.js`) includes `.cshtml`/`.razor`/`.json` alongside the usual JS/TS/C#/etc. set, so ASP.NET Razor views and JSON config get scanned too (not just `.cs`). Every scan upserts an auto-generated `type: "structure"` doc (`PROJECT_STRUCTURE.md`) that's always `enabled: true` and never shown in the file tree for the user to toggle off — `content.js#syncInjectDocsBtn` excludes it when deciding whether the footer inject button should be enabled, so it alone can't make an otherwise-empty selection look injectable. Next to `#codeProjectRefreshBtn` in the documents header sits `#codeProjectIgnoreBtn` (same `.doc-refresh-btn` styling, a circle-slash icon), which opens `#ignorePatternsOverlay` (`history-view.js#openIgnorePatternsDialog`) — a dialog for manually typing file/folder names or `*`-globs to exclude from future scans, stored on `project.ignorePatterns`. Rows can be removed individually; "שמור וסרוק מחדש" persists the list and immediately reruns `rescanCodeProject`, so newly-ignored files drop out of `project.documents` right away. `document-handler.js#scanCodeProject(dirHandle, ignorePatterns)` applies these on top of the built-in `DENY_DIRS`/`DENY_FILENAMES`, matched case-insensitively against either the bare name or the full relative path.
- **Progress indicator (`#scanProgress`, 2026-07-19)** — a **persistent** progress strip below the global project bar (visible from either tab), showing the phase, `done / total`, a bar, and **the file being handled right now**. Owned by `content.js` (`setProgress`/`clearProgress`, siblings of `setStatus`, passed to `history-view.js` through `init` deps); markup in `ui-template.js`, styles in `ui-styles.js`. It exists because `setStatus` is a toast that auto-hides after 2.5s — useless for an operation that runs for minutes. Phases: `discover` / `read` / `graph` / `save` / `load`. Non-obvious details worth preserving: DOM writes are throttled with `setTimeout` and NOT `requestAnimationFrame` (rAF is suspended in a backgrounded tab); `scanCodeProject` reports both on file start and file finish (start-only would leave the counter permanently short by the number of in-flight reads, freezing the bar near the end of every scan); the bar is indeterminate while no total is known; `clearProgress(holdMs)` uses a sequence guard so a held hide can't blank a newer operation's indicator. See `ARCHITECTURE.md`'s "Progress indicator" section.
- **Scan performance (2026-07-19)** — every step of a scan is an IPC round-trip, so the pipeline is latency-bound, not CPU-bound, and is built to keep work in flight: a flat (never recursive — 8^depth) bounded BFS directory walk, a bounded file-read pool, storage writes batched 50 keys per `set`, a single batched `get` when injecting, and a `buildGraph` that yields to the event loop. Per-file `console.log` is deliberately absent — it was measurably a large share of the cost with DevTools open. `included` is sorted by path before returning since concurrent reads finish out of order. Full detail + the measured 11.6× improvement in `ARCHITECTURE.md`'s "Scan performance" section.
- **Timing logs (2026-07-20)** — every file-loading path (`scanCodeProject`, `syncCodeProjectDocuments`, `addDocument`, `injectFilesToChat`, `createCodeProjectBookmark`, `rescanCodeProject`, `runProjectDocumentsInjection` — the "טען קבצים" flow, `fs-handles.js#put/get/verifyPermission`, `dep-graph.js#buildGraph`) **plus the render pipeline** (`content.js#render()`, `history-view.js#render()` — every scan/inject flow ends by calling this, and it was the initially-missing piece: fast scan logs followed by a slow, silent render) logs one `console.log("[ccb-timing] <op>", { ...counts, ...phaseMs, totalMs })` per call, replacing the earlier debug `[ccb-scan]` logging (which leaked `dirHandle.name`/file names). **Hard rule: `[ccb-timing]` payloads are counts/ms/booleans/short enums only — never a file/folder name or file content.** `history-view.js#render()`'s `historyListMs`/`totalBlocks`/`conversations` fields are the ones to check first for "scan is fast but the panel is still slow" — `renderHistoryList()` rebuilds a DOM row per stored conversation on every render. See `ARCHITECTURE.md`'s "Timing logs" subsection.
- **Razor support in the dependency graph** — `.cshtml`/`.razor` files reuse the same C# class/namespace symbol table as `.cs` files (`dep-graph.js#analyzeRazorFile`): any known type name referenced anywhere in the markup (`@model`, `@inject`, tag helpers, embedded `@{ }` blocks) becomes an edge to that type's file, filtered by `@using` directives the same way C# `using`s filter candidates. Razor/HTML comments (`@* *@`, `<!-- -->`) are stripped first so commented-out references don't create false edges. Code-behind pairs (`Foo.cshtml`↔`Foo.cshtml.cs`, `Foo.razor`↔`Foo.razor.cs`) get a guaranteed bidirectional edge on top of the symbol-table scan, since the two files are one logical unit and don't necessarily name-reference each other's types.

## Rules

- After every change: update this file and `ARCHITECTURE.md`
- Keep the current split — never re-merge `ui-modals.js` / `history-view.js` / `chat-features.js` / `content.js`
- When editing dialogs/settings: read `ui-modals.js`. For history/projects/conversation view: `history-view.js`. For GM/save-chat/inject-selected: `chat-features.js`. For mount/wiring/state/edit-form/context-list: `content.js`. For styles: `ui-styles.js`. For prompts defaults: `config.js`.
- Modules access shared state via `_deps.state` and shared helpers via the `_deps` object passed to `init()`. Never read state directly from `window.__ccb*` outside of `init`.
