# Agent Context
_Last updated: 2026-07-21 after fixing large-project structure-doc truncation on injection_

## What This Project Is
Mishley Code Context Bank is a Chrome MV3 extension: a floating sidebar injected into chat sites (Gemini today, an "internal chat" site configurable via `config.js`) that lets the user manage reusable context blocks, a "General Memory" auto-injected preamble, saved conversation history, and projects that can hold fixed text blocks, full documents (files/text/URLs), or an entire local code folder — all injected into the chat on demand. Context management now lives in one place (the Context tab); the History tab is conversations-only.

## Current State
- ✅ Working: sidebar mount/toggle, context blocks, General Memory auto-inject, conversation auto-save + continue flow, prompts editor, context-window meter (incl. per-file token breakdown), project documents (upload/paste/estimate/inject), code-project folder scanning + static dependency graph + file-tree picker. **New:** code projects can now maintain a manual ignore-list (`project.ignorePatterns`) of file/folder names or `*`-globs excluded from scanning, edited via a dialog opened from `#codeProjectIgnoreBtn` next to the documents header's refresh button.
- 🚧 WIP: **the code-project scan performance rework** (2026-07-19) is implemented, harness-verified, and documented, but not yet exercised through the actual extension on the affected machine's real large project. The ignore-list feature below is implemented and documented but **not yet manually verified end-to-end in the browser** (no unpacked-extension test yet), and not yet committed. Earlier items still pending their own browser verification: the prior session's fixes/reverts, and the Context-tab redesign.
- ❌ Known Issues: dependency-graph resolution is best-effort only (dynamic dispatch, computed member access, reflection, `eval` can't be resolved statically — see [dep-graph.js](dep-graph.js) header comment); legacy binary `.doc` files are not text-extractable. **Known-and-deliberately-skipped** (user decision 2026-07-21, stack is React-without-TS + .NET): the dep graph does not do TS NodeNext `.js`→`.ts` mapping, does not analyze Vue/Svelte SFC imports, does not support tsconfig `paths`/`baseUrl` aliases beyond `@/`/`~/`, and silently no-ops (empty deps, "לא זוהו קבצים נוספים") for languages it doesn't analyze (Python/Java/Go/...).

Traced to `history-view.js#runProjectDocumentsInjection`'s per-doc truncation: `const maxChars = doc.type === "code" ? Infinity : 10000` treated the auto-generated `PROJECT_STRUCTURE.md` (`type: "structure"`) as an ordinary text doc, so a large project's full file tree (easily >10,000 chars for a few hundred+ files) was silently cut mid-listing with a `"... Verified with a small Node script simulating both doc types against 15,000-char content (structure/code pass through whole; ordinary text/word docs still cap at 10,000, unaffected). - 2026-07-19 (performance: large code-project scanning was taking many minutes) — A user reported that scanning a full-size code project took a very long time (it did complete, just extremely slowly) while small projects were fine. The cost was per-file overhead × thousands of files, in four independent places, all fixed with no behavior change. (1) **`scanCodeProject` now reads concurrently** — it was strictly sequential (`getFile()` → `text()`, one file at a time, sequential subdirectory descent), and since each of those is an IPC round-trip, almost all wall time was spent waiting. Split into a bounded BFS directory walk (`walkDirectories`, cap 8) + a bounded read pool (`runWithConcurrency`, cap 12). The traversal queue is **flat, not recursive** — recursing into a concurrency-limited helper per level would multiply the cap per level of depth (8^depth). `included` is now sorted by path since concurrent reads finish out of order. (2) **Removed the per-file/per-entry `[ccb-scan]` logging** added last session for the scan-hang investigation — 3–6 `console.log`s per tree entry is tens of thousands of calls on a large project, and each is expensive precisely when DevTools is open. One summary line remains. (3) **Batched storage IO** — `syncCodeProjectDocuments` fired one `set` per file, now batches 50 keys per call (`codeContentPutMany`); the new `docHandler.getCodeContents(docIds)` does one batched `get` for `injectProjectDocuments`, which previously paid a round-trip per selected file. (4) **`dep-graph.js#buildGraph` is now `async`** and yields every 25 files so the tab doesn't freeze; `scanRegions` is cached once per file (it ran up to 3× per C# file) and the combined type-name regex is compiled once per run instead of per file. Also added `onProgress` → status line ("סורק פרויקט... N קבצים" / "בונה מפת תלויות..." / "שומר קבצים..."). Verified with a Node harness on a synthetic 1,452-file tree: **47.6s → 4.1s**, 16 behavior assertions passing. See [CHANGELOG.md](CHANGELOG.md), [ARCHITECTURE.md](ARCHITECTURE.md), [CLAUDE.md](CLAUDE.md).

## Entry Points
- `manifest.json` — content-script load order (source of truth for module boot sequence)
- `content.js#init` — extension entry point; mounts the Shadow DOM UI and wires every module
- `content.js#initModules` — builds the shared `deps` object and calls each module's `init(deps)`

## Key Patterns Used
- Every UI module exposes `init(deps)` and stashes deps privately; state mutations go through `_deps.state` / `_deps` helpers, never directly on `window.__ccb*` (see [CLAUDE.md](CLAUDE.md) Rules section).
- Bulk mutations (e.g. `enableFilesForProject`, `setAllCodeDocsEnabled`) call `saveBlocks()` once, not once per item — looping per-item saves was a real perf bug (each save re-serializes the whole `blocks` object).
- Large or numerous text payloads (file blobs, per-file code content) are kept out of the `blocks` object entirely, in their own `chrome.storage.local` keys, so routine `saveBlocks()` calls (toggling a checkbox, renaming something) stay cheap regardless of project size.
- Anything that touches N files does bounded-concurrency or batched IO, never one round-trip per file: file reads go through a concurrency pool, storage writes are batched per 50 keys, storage reads are one `get` for the whole set. Every one of these is an IPC hop to the browser process, so a per-file loop is latency-bound and scales terribly (this was a real bug — see the 2026-07-19 perf entry).
- Per-file `console.log` in hot paths is treated as a performance bug, not just noise: it's most expensive exactly when DevTools is open, which is when someone is diagnosing slowness. All timing logs use a fixed `[ccb-timing]` prefix, one call per phase/operation (never per-file), and carry ONLY counts/ms/booleans/short enums — never a file/folder name or file content (2026-07-20).
- Static analysis over AI: the dependency graph is a deterministic, no-API-call heuristic — intentionally conservative (favors including too much over silently missing a file).

## Gotchas / Watch Out
- Stored `estimatedTokens` values written before 2026-07-21 used the flat 3.5 divisor — they refresh on the next scan (code files) or when a doc is re-added/re-extracted, NOT retroactively. A mixed panel (old + new estimates) is expected until the user rescans.
- There is exactly ONE chars→tokens policy: `config.js#estimateTextTokens`. Do not add a local `chars / 3.5` (or any ratio) anywhere — that duplication is the bug that was just removed. Same for file heuristics: `document-handler.js` is canonical, `ctx-meter.js` only wraps it.
- `verifyPermission()` in `fs-handles.js` must be called from a user-gesture handler — `requestPermission()` on a `FileSystemDirectoryHandle` throws otherwise.
- Code-project file content is never read back onto `project.documents[].content` — always fetch it via `docHandler.getOrExtractContent`/the `codeContent_<id>` key, or a rescan will silently re-duplicate storage.
- This repo lives under a OneDrive-synced folder with a Hebrew path segment; if OneDrive's cloud file provider isn't running, some files can dehydrate to cloud-only placeholders that `git diff` / file reads fail against with `mmap failed: Invalid argument` or "cloud file provider is not running" — start OneDrive if that happens.
- No bundler/build step — all files are loaded directly as MV3 content scripts in the exact order listed in `manifest.json`; adding a new module means adding it to both the manifest array and `content.js#initModules`.
